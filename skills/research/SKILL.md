## Prerequisite: Ingest External Context

If `$ARGUMENTS` contains any external references (GitHub URLs, repo links, library names, documentation URLs), you MUST ingest them for context before beginning research:

1. **Identify external references**: Scan `$ARGUMENTS` for:
   - GitHub URLs (`https://github.com/...`)
   - Git repo URLs (`https://...git`, `git@...`)
   - Library/package names that are unfamiliar or new to the project
   - Documentation or reference URLs

2. **Run gitingest** for each external reference:
   ```bash
   gitingest <url-or-path> -o ~/code/brain/research/YYYYMMDD/<weight>_digest_<ref-title>.txt
   ```
   - `<ref-title>` is a short, hyphenated slug derived from the repo/library name (e.g., `tanstack-router`, `laravel-reverb`)
   - If the task title already has a digest file, use the same title: `<weight>_digest_<title>.txt`

3. **Read the digest**: After generation, read the digest to absorb project structure, key APIs/patterns/conventions, and integration points relevant to the task.

4. **No external refs?**: Skip this step and proceed to Phase 1.

## Phase 1: Frame the Research

Before investigating, restate the problem so we agree on what we're researching:

1. **Restate the question** in your own words — what decision will this research inform?
2. **Define the research scope** — what questions are in scope, and what is explicitly out of scope?
3. **List the unknowns** — the specific things you don't yet know that this research must resolve.
4. **State success criteria** — what does "enough research to make a confident decision" look like?

Keep this as a short bullet-point summary in chat. If anything is ambiguous, ask me before investigating. Do NOT create a file yet.

---

## Phase 2: Investigate

Work through the problem space methodically. Pull from whatever sources are warranted — the codebase, the ingested digests, web search, and documentation — and keep track of where each finding came from.

1. **Understand the domain**: What problem are we solving? Who are the users? What constraints (technical, business, time, cost) exist?
2. **Survey existing solutions**: What already exists internally (search the repo) and externally (libraries, services, prior art)? Why build instead of reuse?
3. **Evaluate candidate approaches**: Identify 2-3 viable approaches. For each, capture trade-offs across correctness, complexity, performance, security, operability, and cost.
4. **Resolve technical unknowns**: For each unknown from Phase 1, investigate until you can state a finding with a confidence level (high/medium/low) and the evidence behind it. Run small spikes or read source if needed.
5. **Define non-functional requirements**: Performance, security, observability, maintainability, cost, scalability — what will matter for this work?
6. **Surface assumptions and risks**: What are we assuming? What could go wrong, and how likely/severe?

**Cite your evidence.** Every non-obvious claim should point to a source: a repo path (`file:line`), a digest section, or a URL. Distinguish what you verified from what you inferred. If sources conflict, say so. Do not present a guess as a fact — mark low-confidence findings explicitly.

Once investigation is complete and Phase 1 questions are resolved, write the research document at `~/code/brain/research/YYYYMMDD/<weight>_research_<title>.md`.

```markdown

## Existing Solutions / Prior Art

## Candidate Approaches

For each viable approach (aim for 2-3):

### Approach A: [Name]
- **How it works**: Brief description.
- **Pros**: ...
- **Cons**: ...
- **Risk / unknowns**: ...

### Approach B: [Name]
- ...

## Comparison & Recommendation

- A table or bullets comparing the approaches across the dimensions that matter (correctness, complexity, performance, security, operability, cost).
- **Recommendation**: Which approach, and why. Be decisive; state the deciding factors.

- Anything still unresolved, with current confidence level (high/medium/low) and what would resolve it.
```

## Ground Rules (apply throughout)

- **Research, don't build**: This skill produces a document, not code and not a spec. Resist the urge to design the implementation.
- **Evidence over opinion**: Every meaningful claim is backed by a source or marked as an assumption. No unsourced confidence.
- **Be decisive**: A research doc that refuses to recommend anything has failed. State a recommendation even when uncertain — just label the uncertainty.
- **Distinguish verified from inferred**: Make it obvious what you checked vs. what you reasoned about.
- **Ask, don't assume**: If the research scope or the decision being made is ambiguous, pause and ask.
- **Document is living**: If a later phase or conversation reveals new information, update `<weight>_research_<title>.md` so it stays the source of truth.
- **Update AGENTS.md**: If the research uncovered durable facts about the codebase or its constraints (not just this decision), suggest additions/updates to `AGENTS.md` to keep the cached repo memory fresh.
